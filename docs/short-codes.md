# Short Code Generation

The short code is the public key in `shortUrl = host + "/" + code`. It must be short, URL-safe, unique, and generated without a global bottleneck.

## Alphabet: base62

`[0-9A-Za-z]` = 62 symbols. URL-safe (no `+`, `/`, `=` like base64), case-sensitive for max density.

| Length | Keyspace (62^n) | Rough capacity |
|--------|-----------------|----------------|
| 6 | 5.7e10 | 57 billion |
| 7 | 3.5e12 | 3.5 trillion |
| 8 | 2.2e14 | 218 trillion |

Default **7 chars** — trillions of codes, still short. Length grows automatically if the id range demands it.

## Strategy (chosen): Redis atomic counter + base62

Codes are the base62 encoding of a monotonically increasing id, generated by a single **Redis `INCR`**. This makes uniqueness a property of the counter — **no collision check, no retry, no unique-constraint failure on the hot path.** See [ADR-0007](adr/0007-redis-counter-code-generation.md).

```
INCR urls:id_counter  ── returns next unique integer ──▶ base62 encode ──▶ short_code
```

**Why Redis, not Postgres `IDENTITY`, for the counter:**

- Redis is single-threaded — every command runs to completion before the next starts. `INCR` is atomic by construction; there's no read-modify-write race to guard against, unlike a naive `counter++` in application code.
- Two concurrent `INCR` calls always return two different values (e.g. 1000 and 1001) — never the same value twice. This holds true across **multiple Write Service instances** hitting the same Redis, so it solves the multi-instance uniqueness problem for free — no id-range leasing, no per-instance coordination, no Snowflake-style composite id needed.
- One round trip per create (`INCR` is cheap, sub-millisecond) — no batching complexity, unlike leasing id-blocks.
- The id is trivially reversible (`base62 decode → integer`) if you ever need to go short_code → id without a DB lookup.

**Durability trade-off (accepted, documented):** the counter lives in Redis, not Postgres. If Redis loses data, the counter could reset and start re-issuing already-used ids → collision with existing rows.
- Mitigated by `--appendonly yes` in [docker-compose.yml](../docker-compose.yml) (already configured) — Redis persists every `INCR` to its append-only file, survives a restart.
- Defense in depth: the `UNIQUE(short_code)` constraint on `urls` is still the backstop. If the counter ever regresses and reissues a used id, the `INSERT` fails with a unique violation instead of silently overwriting someone else's link — treat that as a hard error to alert on, not a retry-and-continue case.

**Single point of contention:** one Redis counter key is a single logical bottleneck (all instances `INCR` the same key). Acceptable per [scaling.md](scaling.md) — `INCR` throughput on one Redis node is in the tens of thousands/sec, far above this project's realistic write volume. Revisit only if write QPS approaches that ceiling.

## Custom codes (vanity)

`POST /urls` with `customCode`. These bypass id-generation and go straight to an insert guarded by the `UNIQUE(short_code)` constraint:

```sql
INSERT INTO urls (short_code, long_url, ...) VALUES ($1, ...);
-- unique violation → 409 CODE_TAKEN
```

The unique index is the single source of truth for uniqueness — even generated codes rely on it as a backstop.

## Guessability / enumeration

Sequential base62 codes are enumerable (`abc`, `abd`, ...). If links must be private/unguessable:

- add per-user random salt to the encoded id, or
- use random 7-char codes with a uniqueness check + bounded retry (accept the small collision-handling cost).

Default build assumes links are semi-public (share links), so sequential is acceptable and cheaper. Documented as a knob, not a default.

## Collision math (for the random strategy)

Birthday bound: expected first collision around `√(62^n)` codes.

- 7 chars → collision likely around ~1.9M random codes without a uniqueness check.
- With a `UNIQUE` constraint + retry, collisions are *detected*, not silent — a retry loop bounded at 3 attempts handles it; probability of 3 straight collisions at <10% table fill is negligible.

This is why the counter-based strategy is preferred at scale: it sidesteps the birthday problem entirely — no two `INCR` results are ever equal, so there's nothing to collide.
